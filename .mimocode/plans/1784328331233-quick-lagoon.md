# ClinRef AI Integration — Implementation Plan

## Summary

Integrate Koog-based AI assistant into the existing ClinRef UpToDate Viewer app. The agent uses `MedicalDatabaseTools` (already built) to search/retrieve clinical content, streams responses through a SafetyValidator gate, and persists conversations via Room.

---

## Architecture Overview

```
domain/ai/           — Provider abstraction, agent factory, safety validation, streaming
domain/chat/         — Conversation and message domain models
data/local/          — Room DB, DAOs, entities, migrations
data/secure/         — EncryptedSharedPreferences wrapper for API keys
di/                  — Hilt modules (AiModule, DatabaseModule, SecurityModule)
ui/chat/             — ChatScreen, ChatViewModel, composable components
ui/settings/         — AiSettingsScreen, SettingsViewModel
ui/conversations/    — ConversationListScreen
```

## Phase 5: SafetyValidator

### New file: `domain/ai/SafetyValidator.kt`

Provider-independent structural validator. Six rules:

```kotlin
class SafetyValidator {

    data class ValidationResult(
        val passed: Boolean,
        val warnings: List<String>,
        val blockedReason: String? = null
    )

    data class TurnContext(
        val toolCalls: List<ToolCallRecord>,
        val answer: String,
        val citations: List<Citation>,
        val sectionWarnings: Map<String, Boolean> = emptyMap(),
        val toolResults: List<String> = emptyList(),  // raw text returned by each tool call
        val fetchedSections: List<FetchedSection> = emptyList()  // metadata of sections actually fetched
    )

    data class FetchedSection(
        val topicId: String,
        val topicTitle: String,
        val sectionId: String,
        val sectionTitle: String
    )

    fun validate(context: TurnContext): ValidationResult
}
```

**Rule 1 — Tool call required**: Reject if `turnToolCalls` is empty (no successful tool call in this turn).

**Rule 1b — Section content required**: At least one successful `getTopicSectionText()` call must have occurred. Reject if the turn only contains `searchTopics` and/or `getTopicOutline` calls but no `getTopicSectionText` call. This prevents answers based on titles/outlines alone — the answer must be grounded in actual section content.

**Rule 2 — Citation-to-tool consistency**: For every citation in the final answer, verify that:
- The cited `topicTitle` was retrieved in the current turn (exists in `fetchedSections`)
- The cited `sectionId` was retrieved in the current turn (exists in `fetchedSections`)
- The cited `sectionTitle` matches the retrieved section metadata (fuzzy match: `contains` or `equalsIgnoreCase`)

If any citation references content that was not actually fetched, block with "Citation references section not retrieved in this turn." This directly checks grounding instead of using a heuristic similarity score.

**Rule 3 — Complex data warning**: Flag any answer referencing a section with `sectionWarnings[sectionId] == true` unless the answer contains the warning text.

**Rule 4 — No invented numbers (verbatim match)**: Every numeric token in the final answer (regex: `\d+[\.,]?\d*\s*(mg|%|mL|mmol|mcg|units?|mEq|L|kg|cm|mmHg)?`) must appear verbatim (or near-verbatim with unit normalization) in at least one of the `toolResults` from this turn. If any numeric token in the answer cannot be found in tool output, block with "Answer contains numbers not traceable to retrieved source data." This directly enforces "no invented numbers" without punishing legitimate multi-topic comparisons where each fact comes from its own source.

**Rule 5 — Citation required**: Require at least one citation containing exact `topicTitle`, `sectionTitle`, and `sectionId` retrieved during the current turn.

### Tests: `app/src/test/java/com/clinref/app/domain/ai/SafetyValidatorTest.kt`
- Each rule tested independently with positive/negative cases
- Rule 1b: test "searchTopics + getTopicOutline only, no getTopicSectionText" blocks; test "getTopicSectionText present" passes
- Rule 2: test "citation matches fetched section" passes; test "citation references unfetched section" blocks; test "fuzzy sectionTitle match" passes
- Rule 4: test "two independent facts from two sources" passes (each number traceable); test "invented number not in any tool result" blocks
- Combined validation tested
- Edge cases: empty answer, no tools, single citation, multiple citations, cancelled generation

**Model lists** — mixed dynamic/static approach:
```kotlin
suspend fun getAvailableModels(provider: AiProvider, client: LLMClient): List<String> {
    return when (provider) {
        // Dynamic: Koog client exposes .models() — fetch live list
        AiProvider.OPENAI, AiProvider.GOOGLE, AiProvider.DEEPSEEK, AiProvider.OPENROUTER -> {
            try { client.models() } catch (_: Exception) { getStaticFallback(provider) }
        }
        // Static: AnthropicLLMClient and OllamaClient don't expose .models()
        AiProvider.ANTHROPIC, AiProvider.OLLAMA -> getStaticFallback(provider)
    }
}

private fun getStaticFallback(provider: AiProvider): List<String> = when (provider) {
    AiProvider.ANTHROPIC -> listOf("claude-opus-4-1", "claude-sonnet-4-5", "claude-haiku-4")
    AiProvider.OLLAMA    -> listOf("llama3.2", "mistral", "phi3")
    else -> emptyList()  // shouldn't reach here; dynamic path handles it
}
```

Rationale: OpenAI/Google/DeepSeek/OpenRouter model lists change frequently. Fetching via `client.models()` keeps the dropdown current without app updates. Anthropic and Ollama clients don't expose this method, so we maintain small static lists for those two.

## Phase 7: StreamingManager

### New file: `domain/ai/StreamingManager.kt`

Bridges Koog event handlers to Compose `StateFlow`. Important design constraint: `AIAgent.run()` returns a completed result after the full tool-calling loop finishes — it does NOT expose token-level streaming of intermediate text. Therefore this manager streams **tool-call/lifecycle progress only** (confirmed via `handleEvents`), and delivers the final synthesized answer as one SafetyValidator-gated unit. No partial text reaches the UI before validation.

```kotlin
class StreamingManager {
    val agentState: StateFlow<AgentState>
    val toolProgress: StateFlow<ToolProgress?>

    sealed class AgentState {
        data object Idle : AgentState()
        data class ToolCallInProgress(
            val toolName: String,
            val args: String,
            val stepIndex: Int
        ) : AgentState()
        data class WaitingForLlm(val stepIndex: Int) : AgentState()
        data class Completed(
            val result: String,
            val validation: ValidationResult
        ) : AgentState()
        data class Error(
            val message: String,
            val type: ErrorType
        ) : AgentState()
    }

    data class ToolProgress(
        val toolName: String,
        val description: String  // "Searching topics…", "Reading section…"
    )

    enum class ErrorType { INVALID_KEY, NO_NETWORK, RATE_LIMIT, TIMEOUT, NO_RESULTS, UNKNOWN }
}
```

**Koog event wiring** (in `KoogAgentFactory.createAgent`):
```kotlin
handleEvents {
    onToolCallStarting { ctx ->
        streamingManager.onToolCallStarting(ctx.toolName, ctx.toolArgs)
    }
    onAgentCompleted { ctx ->
        val result = ctx.result
        val validation = safetyValidator.validate(buildTurnContext(result))
        streamingManager.onCompleted(result, validation)
    }
    onLLMStreamingFailed { ctx ->
        streamingManager.onError(ctx.error)
    }
}
```

**No `Streaming(text)` state**: The answer is never shown incrementally. Tool progress ("Searching topics…", "Reading section…") provides real-time feedback during the tool loop. The validated answer appears atomically after `onAgentCompleted` fires. This guarantees the SafetyValidator gate is never bypassed.

## Phase 9: ChatViewModel

### New file: `ui/chat/ChatViewModel.kt`

```kotlin
@HiltViewModel
class ChatViewModel @Inject constructor(...) : ViewModel() {
    val messages: StateFlow<List<MessageUiModel>>
    val streamState: StateFlow<StreamingManager.StreamState>
    val toolProgress: StateFlow<String?>
    val configuration: StateFlow<AiConfiguration>

    fun sendMessage(content: String)
    fun cancelGeneration()
    fun startNewConversation(patientProfile: PatientProfile)
    fun loadConversation(id: String)
}
```

**Flow**: `sendMessage` → save user msg to Room → build prompt with history → `agent.run()` in `viewModelScope.launch(Dispatchers.IO)` → observe `StreamingManager.agentState` (tool progress shows "Searching topics…", "Reading section…") → `onAgentCompleted` fires with full result → run SafetyValidator → if passed: save assistant msg to Room, display atomically; if blocked: show error with `blockedReason`, do NOT display answer. On cancel: save a `"cancelled"` role message with partial content for audit trail.

**Cancellation**: `cancelGeneration()` cancels the coroutine `Job`. A `MessageEntity(role = "cancelled", content = "[Generation cancelled by user]")` is persisted so the conversation record is complete. No partial assistant text is shown to the user.

**No incremental text streaming**: `AIAgent.run()` returns a completed result after the full tool loop. Users see tool-call progress (real, from `handleEvents`), then the validated answer appears as one unit. This is by design — it guarantees the SafetyValidator gate is never bypassed by partial text reaching the UI first.

**History compression**: When `tokenCount > threshold`, summarize older messages (excluding patient profile block) via a dedicated LLM call before sending.

## Phase 15: Reliability Layer

### New file: `domain/ai/ReliabilityManager.kt`

- Tool-call timeouts (default 30s)
- Exponential backoff retry (3 attempts, 1s initial, 2x factor)
- Crash-safe message persistence (save user msg to Room before agent call, update on completion)
- **Structured logging with PHI handling**: Regex scrubbing for SSNs (`\d{3}-\d{2}-\d{4}`), medical IDs (`[A-Z]{2,3}\d{6,10}`), and dates (`\d{1,2}/\d{1,2}/\d{2,4}`). **Patient names are NOT regex-scrubbed** — regex can't reliably match free-form names. Instead, the entire `patientProfile` block is excluded from any outbound observability pipeline (Langfuse/OpenTelemetry). The `SecureLogger` strips the `## Patient Profile` section from log messages before they leave the device. Since `PatientProfile` has no name field, the only risk surface is the free-text `notes` field — and the exclusion policy covers that.

## Trade-offs

1. **Room vs raw SQLite**: Room for conversations (type safety, migrations). MedicalDatabaseTools stays on raw SQLite (external DB files). *(Note: external DB source naming is an upstream concern; the AI layer depends on the tool interface, not the backend.)*
2. **richtext-commonmark vs WebView**: Compose-native rendering for better performance.
3. **EncryptedSharedPreferences vs DataStore**: ESP for key encryption at rest.
4. **No token-level streaming**: `AIAgent.run()` returns a completed result after the full tool loop. We stream tool-call progress only (confirmed via `handleEvents`), then deliver the validated answer as one unit. This guarantees the SafetyValidator gate is never bypassed by partial text reaching the UI first. Users see real-time tool progress ("Searching…", "Reading…") which provides adequate feedback during the ~10-30s tool loop.
5. **Agent lifecycle**: Recreated on settings change. History persisted in Room.
6. **Patient profile scope**: Per-conversation, editing starts new conversation.
7. **Dynamic vs static model lists**: OpenAI/Google/DeepSeek/OpenRouter fetch live via `client.models()`. Anthropic and Ollama use static fallbacks (their clients don't expose `.models()`).
8. **PHI handling**: Regex scrubbing for structured identifiers (SSN, MRN, dates). Patient profile block excluded entirely from outbound observability — no regex on free-form names (unreliable).
9. **SafetyValidator Rule 2 (citation-to-tool consistency)**: Every citation must reference a section that was actually fetched in this turn. Replaces the original keyword-overlap heuristic (Jaccard) which produced false positives on legitimate paraphrasing. Directly verifies grounding.
10. **SafetyValidator Rule 1b (section content required)**: At least one `getTopicSectionText()` call must succeed before a clinical answer can be displayed. Prevents answers based on topic titles or outlines alone.
11. **SafetyValidator Rule 4 (verbatim numbers)**: Every numeric token in the answer must be traceable to a tool result. Catches "invented numbers" without false-positiving on legitimate multi-topic comparisons.
